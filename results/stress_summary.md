# 压力测试总结 · 大规模“写作”流程模拟

> 纯桩裸跑（零 LLM、无优化），`stress_write.py`，种子 42。
> 工作流：每章 30 写段 × 33 句 ≈ 990 句/章；段间 tick×1 + assemble；章末 merge_pass；
> 热区改写 10%、回改 5%（编辑上一章）、每 10 段检索一次。
> 参数：decay=3, 阈值=30, 父卡HP=70, 热阈值=60, 秩差=1, cap=500 原子。

## 二、关键发现

### 亮点（设计主张在规模下成立）

1. **正确性**：31 次抽样不变量全过（链序、发射覆盖、数值 oracle、占位语义、高度一致性）——30 万句 + 4050 次编辑下标记/重建/合并机制无一处破坏。
2. **铺陈项数恒定 765~766**：规模 ×30（1万→30万），铺陈大小几乎不变——基础层被当前章热区约束，与全书规模无关。“近热远粗”的 token 恒定主张在规模下成立（组装 0.14→0.22ms 也基本恒定）。
3. **树高亚对数**：1万→4、5万→9、10万→10、30万→13（log2(30万)≈18、sqrt≈548）——按秩合并（秩差=1）把顺序追加的梳子压成亚对数；若不加规则，303 章顺序追加 ≈ 303 层。
4. **LLM 成本代理**：30 万句全书 merge 1133 次 / rebuild 4217 次 → 每章约 3.7 次合并蒸馏 + 13.9 次重建 ≈ 18 次 LLM 调用/章（与 token 预算同量级，可接受）。

### 瓶颈（实现级 O(n) 墙，需在真实系统解决）

1. **`_position_map` 每次 O(全书原子数)**：write / retrieve / edit 全部被它主导（30 万句时 write 12ms、edit 24ms、retrieve 12ms，占总耗时 ~60%）。
   来源：每次写入都要做 archive 区间相交检查（`_staleArchive`），每次检索排序也要全链位置图。
   这正是 AGENTS.md §11“卡片规模上限：暴力 vs 索引”悬案的裁决数据——必须上索引：
   archive 区间索引（编辑时按区间查询，而非全表扫描）+ 顺序维护结构（order-maintenance，避免全链位置图）。
2. **衰减 O(全书) 且每段一次**：tick 12.6ms @30万 × 9000 次 ≈ 113s。真实系统需批量/惰性 HP。
3. **归档增长与重建线性**：30 万句 → 4217 条归档（80% 已 stale）；stale 扫描随编辑次数线性增长，索引后可消除。
4. **drop 事件为 0**：本轮模拟无“整节点删除”场景（回改只删 3 句），节点回收路径未被规模覆盖——属测试盲区，真实回滚/整章重写场景需要补测。

### 结论

- 机制正确性在 30 万句规模成立，树形与铺陈的规模无关性被证实；
- 裸桩可支撑 ~30 万句的模拟（5 分钟）；再往上（50 万~100 万句）耗时线性增长且受 O(n) 墙限制，建议在真实实现中直接采用索引方案，桩保持现状作为行为基准。
