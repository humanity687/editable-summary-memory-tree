# 分层记忆树 v2 · 参考资料上下文管理运行时 — 全文复述

## 一、主题与定位

这是一套"分层记忆树 v2"参考资料上下文管理运行时，核心目标：把一份长参考资料变成"位置有序、分辨率可变、可编辑演化"的记忆树，让 Agent 在有限上下文窗口里稳定工作于任意规模的参考资料之上。当前状态：机制层已实现并多场景实测，桩引擎 `core.py` + 真实引擎 `realtest/realengine.py`，`tests/` 303 全绿；已在小说写作 / 聊天智能体 / 代码智能体 / ahi-bench 四类场景实测。参数台账（`AGENTS.md §11`）已与代码逐项对齐，数值校准仍在进行。

近期（2026-10）：人格保持实验完成 tree/flat 首轮对比 + `style_alpha` 消融 + `self_quota` 操控（120 轮）；结论：趋同根因 = 树管线 / 跨 agent 耦合；`self_quota` 抬自我可见性有效（词面趋同归零）但**未止住人格漂移**（p1 锚到"污染态自我"）——详见 `AGENTS.md §4.5.10`、`ahi-bench/PERSONA_RETENTION.md §10.3.1`、`ahi-bench/PR5_REPORT.md`。

## 二、要解决的问题

一份长参考资料（一本书全文、大型文档集）无法整体塞进有限上下文窗口。已有三种做法各有致命伤：

| 做法 | 问题 |
| 全量发送 | 窗口爆炸，且"塞得下"≠"记得住"（注意力衰减） |
| 静态摘要拼接 | 丢细节，无法承载状态演化 |
| 关键词检索 | 无状态、无结构，检索片段孤立无上下文 |

核心矛盾：参考资料是"长期演化的内容"，而现有方案都在用"无状态的文本生成"去逼近它。

## 三、核心思想（四条）

1. **位置有序的记忆树**——参考资料切成原子卡（句粒度），按原文顺序组织；摘要卡按连续区间自底向上合并成树。树的任何节点 = 某一段连续区间的概括。
2. **分辨率随热度变化**——近处（当前工作区）全分辨率原文，远处自动降为各级摘要；越老的记忆越粗、但越稳定。
3. **编辑即失效，重建即蒸馏**——任何修改精确地使受影响区间失效，被改内容立即从所有查询中排除；重建全部推迟到蒸馏时机，编辑路径本身零 LLM、零阻塞。
4. **不可遗忘的事实层**——与正文流分离的"笔记本"：无衰减、全量存储、按需注入。负责跨区引用（伏笔/回调）与硬约束，不做概率性召回。

## 四、架构一览

三轨记忆（当前=进程内 + gzip/JSONL 快照；SQLite 为规划目标）：
- 轨道A 参考资料流：记忆树 + 原子层 + 历史归档
- 轨道B 笔记本：常驻约束 / 状态条目 / 调度条目
- 轨道C 工作记录：工具组压缩卡，自然遗忘

调度原则：组装每次工具调用一次，纯计算（零 LLM）；蒸馏在章节边界 / 预算超标 / 低 HP 承压条件式触发。

关键机制：
- **近热远粗的上下文**：每个工具调用时，上下文 = 全局概述层 + 与当前任务相关的召回路径 + 最近工作区的全文原文，预算恒定。
- **区间失效**：任何编辑（AI 工具或用户界面，同一条路径）通过位置区间精确失效旧内容，改动区域立即从"摘要层"剥落为"原文层"，衰减后自动重新融合。
- **检索不挑深度**：对整棵记忆树打分，命中节点连同其祖先路径一并注入；精确引用走独立的逐字校验通道，杜绝"回忆变编造"。
- **事实不遗忘**：伏笔、设定、角色状态存放于独立笔记本，按当前任务目标精确选取注入，全量存储、绝不衰减。

## 五、首个应用：长篇小说写作 Agent

- 分阶段写作（write / rewrite / edit / recall / ask），每章一个固定流程：目标进入 → 预检索 → 写作循环 → 章末蒸馏 + 事实对账 + 版本快照。
- 伏笔（调度条目）按埋设/推进/回收窗口强制注入；章节完成时自动"对账"：新章事实声明与笔记本比对，冲突由作者裁决。
- 每章恒定 ~16k 字符上下文预算，与全书规模无关。
- 通用化：章 → 结构单元，beat → 内容块，伏笔 → 跨区引用账本。同样适用于代码库、研究文档、项目资料等任何"参考资料"场景。

## 六、实验计划（先于功能验收）

1. **属性测试**：编辑标记完备性、铺陈不变量、边界条件穷举、回滚对称性。
2. **延迟回忆基准**：固定大纲写 20 章 → 续写第 21 章 → 检测对第 1 章伏笔/角色的引用正确率，与"全量发送 / 摘要拼接"对照。
3. **状态一致性基准**：注入事实变更（改名/死亡/恢复）→ 检测后续章节一致性。
4. **token 计量** 与 **人类找茬**。

## 七、交互演示与里程碑

## 五、核心设计决策（为什么是现在这样）

1. **稳定 ID + 顺序链表（piece-table 式）**：编辑不做全局坐标平移；区间只用位置序判断，禁 ID 大小比较。
2. **区间覆盖树，并查集式自底向上合并**：父 = 子区间的概括；无预设根；深度 = 合并历史。
3. **按秩合并（`merge_depth_diff=1`）**：防梳子退化，顺序追加亚对数（实测 64 批 → 高 9）。
4. **禁止单成员块**：父节点创建时子数 ≥2。
5. **收养机制**：插入原子按两侧边界 owner 链 LCA 入树；缝隙在边界/首尾 → 不收养。
6. **标记置脏（唯一算法）**：删除爬墓碑卡链、插入爬收养链；完备性引理：区间相交 ⟺ 爬链必经。
7. **占位解除 = 冷却重建**：全部存活子卡 HP < hot_threshold → 重建解占位。
8. **重建级联**：重建后父卡置脏 → 同 pass 循环至无脏。
9. **影子注入（召回进组装）**：位置槽 = 覆盖它的发射项之后，沿 owner 链下钻 O(深度)。
10. **从属标注（硬要求）**：深度缩进 + ⊂父卡 + "召回影子/召回原文"标注。
11. **提升（路径分裂）**：激活计数达阈值 → 节点沿祖先逐层上提，每层祖先分裂左右碎片。
12. **混合检索三通道**（缺陷 B 修复）：摘要·向量（bge-small-zh）+ 摘要·关键词（bigram）+ 原子·粗筛+向量精排。
13. **回滚**：undo 逆向走编辑路径；多原子块恢复用末原子锚点。
14. **注意力窗口（§4.3b，2026-08-12 实现）**：窗口内 = 存活原子按 HP 降序排名 ≤ attention_cap 且 HP ≥ attention_out；不对称衰减（窗内 ×in_decay 慢 / 窗外 ×out_decay 快）。
15. **force 合并（窗外压力）**：铺陈中窗外原子数 > attention_cap × pressure_threshold → `merge_pass(force_out=True)`——只合并纯原子段。
16. **叶子展开（C 机制）**：检索命中节点 → 展开其全部后代存活原子为影子（活一轮、预算保护、上限 EXPAND_ATOM_CAP/CHAR_CAP）。
17. **run2 协议（无尽续写 v2）**：`[plan]`写前预想 → `[recall]`/`[span]` 回想 → 正文 → `[note state]` 状态入笔记本。
18. **冷却窗口（bench_qa 专用）**：风暴后 tick(45)→merge→tick(30)→merge。
19. **merge 条件式触发（2026-08-30 拍定）**：常规 merge 从时间式（merge_every=4）改为每轮查 `merge_pressure()`——铺陈窗外节点数+窗外原子数（weight 计）> `merge_pressure_threshold`(20) 即蒸。模拟：tiling 峰值 215→143、谷底 127→25。
20. **节点窗口扩展（2026-08-30 拍定）**：注意力节点段成员从"铺陈节点"改为"全部存活节点"。

Commands：安装依赖、启动主进程、启动特定 agent、停止 agent。无测试套件或 lint 配置。

Architecture：进程模型；消息流（4 步）；关键抽象（`BaseAHIAgent`、`AgentRunner`、`PythonShell`、`LLMClient`）；Agent 创建模式；Agent 结构化响应格式；配置。

## ahi-multi/next_exp_insts.md

标题：遗言恰恰是反证——你看到的趋同在词汇层，细读立场层，60轮人格稳定性的最强证据就藏在这三份遗言里。

一、"说法都差不多"的分层裁决：词汇融合，立场分化。换框架测试结果相反；四层信号模型补完（词汇/模板/着重点/立场）。

二、指纹数据先别判预言2——neutral 没开染色，指纹也动了。三种假设 H1/H2/H3；判定前必须做内容类别控制。

三、neutral 遗言的高重放率有机制原因——这个教训直接进缺席实验。时间线：21:56:08 林深遗言广播 → neutral 挂起 8 分钟 → 22:05:50 恢复 → 首组装大量检索命中积压的林深遗言 → 复用。

四、缺席实验：加一个皇冠操纵和一个被漏掉的模式变量。模式选择（停机缺席 vs 独处缺席）；皇冠操纵（冷/热缺席）；预注册预言表（6 条）；陷阱清单（5 条）。

五、两个 bug 的决策：join 无超时（迁移到 `concurrent.futures`）；inject 身份（预注册 `user:experimenter`）。

六、优先级：P0 / P1 / P1 / P2 / P2。
