这份文档是 `realtest/editbench/EXPERIMENT_REPORT.md`（编辑风暴实验报告，2026-09-27 ~ 2026-10-01），汇总本会话在 `realtest/editbench/` 上搭建框架并运行的全部实验。核心要点如下：

**主题与结论**
- 非论文定稿数字：多为单文档、单 seed、1~3 遍，正式轮参数仍在收敛。设计权威 = 根 `AGENTS.md`；运行细则与历史见 `HANDOFF.md §4.13/§4.14`。
- 编辑失效机制可用：原子层旧值一律 0 存活，新值齐全（rename/detail/passage/delete 全部到位）；摘要层基本干净（仅"时序分流"把旧值作为历史叙述，非残留）。
- 三个真 bug 已定位修复：① 整段改写（多句）在 `分层树臂.apply_ledger` 未进树；② 冷却窗口缺失导致占位卡淹没 QA；③ `delete` 整卡误删（列表行被并进大原子）。另修冷却过量致整树压平（§3.8）。
- 一个负结果：叶子展开按"替换摘要为原子"实现 → 明显变差（低 HP 原子被裁剪）。
- 参数收敛方向：`initial_hp` 100→70（组均继承保留、节点 HP 一般高于原子初始）；`retrieval_budget` 20 + `assembly_budget` 24k；编辑后最小冷却（`_COOL_TICKS=4`，§3.8），非"越大越好"。
- seed2 3×8 正式轮（cool=4）：追加式延续反转崩 12–16/45、复述残留 39–89%（上下文腐烂）；tree 增量与重建持平（反转 41≈42）且复述反超（100% vs 71%）、残留 0%（§2.5）。
- 成本主因：tree 的缓存前缀命中率低（20–42% vs full/flat 94–98%），且构建/冷却的蒸馏调用量随文档线性增长。

**框架（§1）**
- `docbench.py`：编排 P1 四结构基线 → P2 编辑风暴 → P3 8 臂（rebuild/incremental）→ P4 复述。
- `arms.py`：full / flat(400字chunk+bge+top12) / 递归聚簇树 / 分层树；每臂蒸馏(temp0)+作答(temp0.5) 双 client。
- `editstorm.py`：确定性编辑序列 + 台账（rename/detail/rewrite/passage/delete/append）。
- `layerscore.py`：分层判分（反转/不变/远端）+ 复述两层。
- `judge.py`：LLM 判分（temp0）：反转语义判 / 复述残留。
- `cache_probe.py`：KV 缓存前缀命中探针。
- `bonus.py`：编辑效果分析（摘要旧内容残留 + 重写段连贯性）。
- `gen_script.py`：ahi 实录 → 剧本《沙箱四声》。
- `questions_full.json` / `questions_ahi.json`：题库。
- 方案 A（用户拍定）：编辑 1 次、构建 1 次，只重复作答；每臂 API key 隔离计费。

- §2.2 tree 预算对齐（`out/full_r3_tree7k`，tree-budget 7000）：inc_tree 每问 4178 token 且稳定，prompt 总量 1.54M→0.85M（−45%）；inc_tree 反转 13/15→15/15。其余臂不变。

**关键发现（§3）**
- §3.1 编辑机制正确（原子层）：失效路径（delete→爬链置脏；插入→收养链置脏）正确。
- §3.2 占位卡 + 冷却窗口（QA 崩溃的根因）：编辑产生的新原子（原 HP=100）在祖先链上触发占位卡（value=None）。`settle` 仅 `tick(1)+merge` 时，实测 181/527 节点为占位、tiling 61→32，QA 组装体只剩"【占位：概要暂缺】"→ 反转 1/5。修复：加冷却窗口（就地验证：占位 181→0，QA 9/22→18/22）。但 `tick(45)+tick(30)` 过量——全树 HP 归零 → merge 把整篇压成 3 个根摘要（§3.8），最终收敛为最小冷却 `_COOL_TICKS=4`。`initial_hp` 100→70 后占位期从 ~10 tick 缩到 ~2.5 tick，冷却只需数轮。
- §3.3 摘要粒度 → 针尖检索（固有边界）：全局视图仅 ~875–2358 字承载 147k 原文；摘要层旧/新细节常为 0（细节只活在原子）。QA 能否答对取决于检索能否命中原子。`retrieval_budget` 6→20 + budget 24k 只带来边际改善；叶子展开（替换摘要为原子）为负结果（低 HP 原子被 `_trim_chars` 优先裁掉，反而丢掉摘要）。
- §3.4 编辑效果 bonus：摘要旧内容残留——6~10 编辑中绝大多数干净（存活摘要节点旧值 0）；唯一残留是"时序分流"把旧值作为历史叙述（如"早期单进程…结论为双进程"），是设计特性，非失效遗漏 → 指标须改 judge（"旧值是否被当作当前事实"）。重写段连贯性——LLM judge 判"否"：只改一行、同类断言文中尚有 15+ 处 → 新文档自相矛盾；取全局唯一断言（b 项）重做后不再矛盾。全局视图旧值泄漏 0；原子层新旧完全正确。
- §3.5 缓存前缀稳定性：见 §2.3。tree 前缀不稳定（每问重组装 + 影子按位置槽插流）→ 低命中；这是 tree 成本高的结构性原因。
- §3.6 本会话发现的 bug：① 整段改写未进树（真 bug，已修）：`分层树臂.apply_ledger` 无 `passage` 分支；且按"整段 582 字"找原子子串（句子粒度）必然不命中。改：`editstorm.replace_passage`（old/new_units = 句粒度）+ tree 走 `rewrite` 分支。② 冷却缺失（设计缺口，已修）：见 §3.2。③ 叶子展开实现有害（负结果，已回退）：见 §3.3。④ 温度重复无方差（方法学）：temp=0 下重复 N 遍逐位相同。⑤ 确定性片段判分脆弱：会误伤"引旧文再标已删除"；`norm_cjk` 去标点导致跨句误匹配（如 `四面墙，四个高度`）。
- §3.7 审查追加修订（2026-10-01 收尾：公平性/效度）：① `delete` 整卡误删（真 bug，已修）：`分层树臂.apply_ledger` 对「值含目标句」的原子整卡墓碑，但聊天列表行常被 `split_sentences` 并进一个大原子（实测一处 328 字原子含 `pid: 1`/`procs`/可写路径）。整卡删除连带删掉未指定删除的事实，使 inc_tree 信息严格少于 ground-truth `new_doc` 与 reb 臂（存档核对：删后存活原子 `pid: 1`=0）。已改为只移除目标子串、保留残句（`arms.py`），确定性回放验证 `pid/procs/writable` 保留。顺带修 `judge.py` 三级容错失效（正则层返回 `field/value`、消费端读 `verdict/rot`，第 3 级形同虚设）。② passage 修复未验、旧跑作废：`ahi_tree_hp70` 在 16:23 修复前完成——存档 `inc_edited` 仍含 `6 个路径`。③ 判分流水线（省成本，已改）：确定性初筛通过即过；仅失败样本过 judge 复核（`run_qa`），消 `forbid` 子串对「引旧文并说明已改」的误伤——该误伤不对称，恰好压在最谨慎的 tree 臂上。`docscore.check_spec` 改句内匹配（先按句末标点/换行切段再归一匹配），消灭 `norm_cjk` 去标点导致的跨句拼接误命中。④ 使用史 = 分离而非删除（已改框架）：使用史（HP/recall_boost/activation/promote）是 inc 策略的内禀组成，保留。新增 `inc_cold_tree`（无 Phase 1 使用史的旧文树 + 同一 `apply_ledger`），把 H3 拆成 `inc_cold vs reb`（纯原地失效）与 `inc_warm vs inc_cold`（状态连续性）两个因子。所有臂在 Phase 2 结束点（reb 在构建完成点）打快照，每遍作答前 `restore` → 重复测量独立。⑤ 预算：接受为结构属性、主表不对齐；新增 `--flat-topk`（附录 flat@6/12/24 敏感性），tree@7k/16k 已有开关。⑥ 统计口径（run 脚本已改）：作答 `--answer-temp 0.7`、`--repeats 5`、启用 `--judge`；`tests/` 267 全绿。（5 类 × 3：rename/rewrite/detail/delete/append）。15 题经评分器级锚点校验：before 唯一且在原文、after 唯一且在新文、两侧互斥（`bad=0`）。ahi-act 扩题已完成（11→16，5 类）。
- §3.8 冷却过量 → 整树压平（复述塌陷的根因，已修）：`分层树臂.settle` 原为 `tick(1)+merge; tick(45)+merge; tick(30)+merge`。`decay=8` 时约 9 tick 全卡 HP 即归零，75 tick 使全树都成"低 HP" → `merge_pass` 把整篇一路合并到根：实测 `inc_edited` 铺陈 50→3（~600 字）、复述覆盖 100%→14%；重建臂只走 `build` 节奏（无冷却）→ 铺陈 23、覆盖 71%。这是流程不对称，非编辑机制缺陷。修复：`settle` 改最小冷却 `tick(1)+merge; tick(_COOL_TICKS)+merge`（`_COOL_TICKS` 默认 4，env 可覆盖）。Dummy LLM 结构重放：旧 schedule 编辑后 27→2；cool=4 → 18（占位 0）；cool=0 → 21（占位 23 未解）；cool=8 → 5（过并）。真实重放（N=1）：inc 铺陈 3→33、复述覆盖 warm 14%→100%、cold 43%→86%。warm 的 recall 回血高 HP 节点需 ~12 tick 才降到 hot 以下，故仍有 5 个占位（可接受；纯冷树为 0）。
- §3.9 append 臂改用 function-calling 块（公平性关键修正）：旧版 full/flat/递归聚簇树 把编辑结果平铺 dump 到上下文末尾。full 反转仅 12/45，看似"tree 大胜 full"——但这是格式假象。改为逐次工具调用的 function-calling 块（`<tool_call name="edit_document">{args}</tool_call>` + `<tool_result>新内容</tool_result>`，`editstorm.tool_block_units`）后：full 反转 12→41、flat 15→21、递归聚簇树 16→23；格式公平后 `inc_tree 41 ≈ inc_full 41 ≈ reb 42–45`——反转轴无结构大胜，tree 独有优势落在复述轴（100%/0%）。避免 reviewer 批"基线故意给差格式"。flat/递归聚簇树 各编辑块作为可检索条目追加。
- §3.10 A/B：编辑作"使用信号(热) vs 障碍(冷)"（matched-pair）：`ab_edit_signal.py`：同一棵 pre-edit 树（warm/cold）分别施加 on/off 编辑，唯一差异 = 编辑新原子 HP（seed2, N=3）。复述轴 signal 一致更好（warm 100% vs 86%、cold 81% vs 71%，逐遍一致、0 残留）→ 编辑作使用信号显著提升全局巩固。Q/A：冷树 signal 更好（103 vs 97，反转 42 vs 34）；热树 signal 略差（101 vs 108，反转 40 vs 42）。结论：可主张"编辑作使用信号利于全局巩固"，不可主张"Q/A 一律更好"（热冷权衡）。完整表见 `REPORT.md` §3；产物 `out/seed2_ab_editsignal/`。
