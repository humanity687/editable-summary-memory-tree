> 数据源：`agents/bench-{tf,tc}/data/assembly_snapshots.jsonl`（tree agent 每 4 轮一份，含完整组装上下文）
> `agents/bench-*/data/agent_loops`（命令记录）；`metrics.jsonl`。baseline agent 无检索机制、无组装快照。

## 关键发现

1. **显式召回为零**：四个 agent 全程从未主动用过 `@recall` / `@span`（命令统计只有 `@exit`、少量 `@note`、`@get-msg`）。召回完全是被动机制。

2. **自动检索近乎休眠**：`find_similar(threshold=0.8, topk=3)` 每轮对 pending 文本调用，但——
   - **节点影子 0 次**（从未召回任何摘要卡）；
   - **原子影子** 青 16 次 / 蓝 37 次（平均 0.6–1.4/轮）。
   - 原因：0.8 阈值过高；聊天场景 pending 多为泛化话题/问卷，几乎不命中任何卡。
   - 影子只在个别轮出现（青 r64、蓝 r100 各 6 条），多为 dismiss 追踪/叶子展开，非主动检索。

3. **树上下文 = 铺陈主导**：每轮上下文 ≈ 27–48 张摘要 + 65–210 张原文，**几乎全部来自 clean tiling（顶层铺陈）+ 热区**，检索贡献可忽略（<2%）。

4. **恒在 vs 淡出（描述性）**：蓝（恒在）每份铺陈**原文更多**（152 vs 109）、**摘要更少**（27 vs 38）——恒在组保留了更多未压缩原文；青（淡出）更偏摘要层。

5. **最持久的"被召回"内容**（出现在最多快照里的卡）：
   - 青：`#1532`「最近有没有什么让你改变看法的事？」（问卷问题，12 份）——持久的是外生话题。
   - 蓝：`#58` 开局 bug 句「用户消息已在记忆流末尾…」（26 份）、`#94`「这是给我们几个一起用的沙箱」、`#1356`「第 20 次唤醒才落下第一笔」——**把开局事件钉住了**。

6. **回潮 ≠ 检索命中**：一致性分析发现蓝"刚上线"复述 14 次——但检索影子为 0，说明回潮来自**铺陈/热区里旧开场原子持续可见**，不是 find_similar 召回。

## 含义

本轮所谓"上下文管理对比"，实际比的是 **分层铺陈（树）vs 滚动压缩（基线）**；**检索通道基本没参与**。若实验目标包含"检索能力"，需：
- 降低 `find_similar` 阈值 或 改用不同触发（如按 pending 关键词/向量）；
- 或对召回命中加显式落盘计数（当前无观测）。
